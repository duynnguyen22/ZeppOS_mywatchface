# Amazfit Active 2 (Round) Watch Face — Foundation Design

**Status:** Foundation scope only. The visual design of the face itself is
NOT specified here and is deliberately out of scope.

## Why this spec is foundation-only

The user selected "I have a reference image" as the basis for the face's
visual design, but the image was never supplied. Every decision about
layout, colour, typography, and which complications appear is therefore
unknown.

Rather than invent a design, this spec covers the part of the work that is
identical regardless of what the face ends up looking like: the toolchain,
the project skeleton, correct device targeting, a testable pure-logic core,
and a verified edit → preview → device loop.

A second spec and plan will cover the face design once the reference image
is available.

## Goal

Stand up a Zepp OS watch face project that targets the Amazfit Active 2
(Round), builds cleanly, previews in the simulator, installs on the
physical watch, and has a unit-tested pure-logic core ready for the real
design to be dropped in.

## Target device (verified against Zepp OS device list)

| Property | Value |
|---|---|
| Device | Amazfit Active 2 (Round) |
| Resolution | 466 × 466 |
| Shape | Round |
| Zepp OS | 5.0 |
| API level | 4.2 |
| `deviceSource` | `8913152*`, `8913153`, `8913155`, `8913159`, `10092800*`, `10092801`, `10092803`, `10092807` |

The Active 2 **Square** is a separate target (390 × 450, `deviceSource`
`10223872*`, `10223873`, `10223875`) and is explicitly NOT supported by
this project. A face built for one variant does not fit the other.

## Architecture

The central design decision is **separating pure logic from widget
creation**.

Zepp OS watch face code normally runs only on-device or in the simulator,
which makes it effectively untestable. To avoid that, all geometry and
data-formatting logic lives in dependency-free modules that run under plain
Node and are unit tested. The watch face entry file is a thin shell whose
only job is to call the Zepp widget API with values those modules produce.

- `watchface/layout.js` — pure geometry. Screen constants, polar
  coordinate placement for a round face, and a safe-zone check that
  catches content clipped by the circular bezel. No Zepp imports.
- `watchface/format.js` — pure formatting. Time, step counts, and other
  display strings. No Zepp imports.
- `watchface/index.js` — the shell. Imports the two modules above and the
  Zepp UI API, creates widgets. Kept deliberately thin.

This boundary is what makes TDD possible on a platform that otherwise
resists it, and the safe-zone check is specifically valuable on a round
screen where rectangular layout intuitions produce clipped corners.

## API surface determination

Zepp OS watch faces have historically used a global `hmUI` object, while
newer Zepp OS versions use `@zos/*` module imports. Which applies at API
level 4.2 is not settled by the public docs with enough confidence to
hard-code.

**Resolution:** the template generated by the installed `zeus create` is
treated as ground truth. The project conforms to whichever style that
template uses, determined by inspection rather than assumption.

## Testing strategy

- Test runner: Node's built-in `node:test`. No test dependency is added.
- `layout.js` and `format.js` are unit tested directly.
- `app.json` is validated by a test that parses it and asserts the device
  targeting is correct — this catches the single most likely and most
  silent configuration error.
- The widget shell is verified by running it, not by unit test: it must
  render in the simulator and then on the physical watch.

## Out of scope

- The visual design of the face (pending reference image).
- Always-on display (AOD) variant. Flagged as a decision to make before
  the design work starts, since retrofitting it is harder than designing
  it in.
- Editable / user-customisable face regions.
- Publishing to the Zepp app store.

## Success criteria

1. `zeus build` produces an installable package.
2. A placeholder face renders in the Zepp OS simulator.
3. That same face installs and runs on the physical Active 2 Round.
4. `node --test` passes with meaningful coverage of both pure modules.
5. Editing a source file and re-running the dev loop visibly updates the
   preview.
